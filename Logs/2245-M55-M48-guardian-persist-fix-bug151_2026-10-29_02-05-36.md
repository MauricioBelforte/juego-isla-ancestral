## 2. M55 L130 - guardian de 3 capas en test_diario_persist.gd

### 2.1 El hueco, medido antes del cambio

El baseline real, corrido antes de tocar el archivo:

```
EXIT=0 | === TEST M55 PERSISTENCIA: 0 fallo(s) ===
```

Ese "0 fallo(s)" **no tenia contador**: `_check()` solo incrementaba `_fallos`, nunca un total;
no habia `CHECKS_MINIMOS`; no habia `_summary()`; y `quit()` vivia al final de `_run()`, asi que
un `SCRIPT ERROR` que abortara una fase dejaba **menos checks ejecutados** y el proceso salia
EXIT 0 con "0 fallo(s)". Falso verde latente, familia de las trampas 63/85/122.

### 2.2 Lo implementado (5 capas, no 3)

1. `_checks += 1` en **cada** `_check()` (no solo al fallar).
2. `CHECKS_MINIMOS_PADRE` y `CHECKS_MINIMOS_HIJO`: **por fase**, porque son dos PROCESOS
   distintos y no miden lo mismo. Pisos MEDIDOS en verde (seccion 2.3), no estimados.
3. `_arrancar()` -> `await _run()` -> `_summary()`. NO se difiere `_summary()` desde `_init()`:
   con `await` dentro de `_run()`, un `call_deferred` separado corre en el PRIMER await y
   declararia fallida una suite correcta (trampa ya medida en esta memoria).
4. Marcadores `_fin("padre")` / `_fin("hijo")`: el resumen NOMBRA la fase que no cerro.
5. **Reporte JSON del hijo.** El padre solo veia el exit code del hijo; su cobertura era
   invisible. Ahora el hijo escribe `checks/fallos/terminado/bloques` en
   `%TEMP%/isla_diario_persist_hijo.json` y el padre lo lee y lo asevera.

Extra de seguridad: el backup del slot 3 del usuario (`_prev_save`/`_prev_bak`) paso a ser
miembro y `_summary()` lo restaura si una fase aborta a mitad. Antes, un aborto dejaba el save
del usuario pisado por el fixture. `_backup_capturado` distingue "no hay nada que restaurar" de
"hay que borrar un archivo que no existia" (sin esa bandera, un aborto temprano habria BORRADO
el slot).

### 2.3 Pisos MEDIDOS (primero se corrio con piso 1, se leyo el numero, despues se fijo)

```
[bloque padre] checks acumulados: 10
=== Resumen M55 PERSISTENCIA (padre): 10 checks, 0 fallos ===
reporte hijo: {"bloques":["hijo"],"checks":11,"fallos":0,"terminado":true}
```

=> `CHECKS_MINIMOS_PADRE = 10`, `CHECKS_MINIMOS_HIJO = 11`.

Verde x3 tras fijarlos: `EXIT=0 | 10 checks, 0 fallos` en las 3 corridas, `SCRIPT ERROR = 0`.

### 2.4 Sondas EN ROJO (7/7), con restauracion por sha256

El padre lanza al hijo por ruta `res://` fija, asi que mutar una COPIA no servia: se muto el
archivo real, se corrio Godot y se restauro desde los bytes originales verificando sha256 en
cada sonda. Control verde ANTES y DESPUES.

| Sonda | Mutacion | Resultado medido |
|---|---|---|
| control | ninguna | EXIT 0, `10 checks, 0 fallos`, sin `[FAIL]` |
| A | piso padre 10 -> 11 | EXIT 1 + `[FAIL] solo 10 checks ejecutados ... (minimo medido 11)` |
| B | aborto de RUNTIME dentro de `_fase_padre` | EXIT 1 + `[FAIL] el bloque padre NO se ejecuto` + `[FAIL] solo 1 checks ejecutados` + `SCRIPT ERROR` |
| C | aborto de RUNTIME dentro de `_fase_hijo` | EXIT 1 + `FALLO: hijo verifico la carga (exit=1)` + `el hijo reporta 0 fallos (obtuvo 2)` + `el hijo ejecuto >= 11 checks (obtuvo 1)` |
| D | `_fin(FASE_PADRE)` suprimido | EXIT 1 + `[FAIL] el bloque padre NO se ejecuto` |
| E | piso hijo 11 -> 12 | EXIT 1 + `el hijo ejecuto >= 12 checks (obtuvo 11)` |
| control final | ninguna (archivo restaurado) | EXIT 0, `10 checks, 0 fallos` |

La sonda B es la que demuestra el falso verde original: el aborto ocurre dentro de una FUNCION
AUXILIAR, `_run()` continua y termina "bien", asi que una bandera `_terminado` NO lo detecta.
Con 1 check ejecutado y 0 fallos, el codigo viejo habria impreso "0 fallo(s)" y salido EXIT 0.
Lo que lo caza es el piso + el marcador de bloque.

**Defecto propio corregido en el camino:** la primera pasada del arnes dio 5/7 porque yo esperaba
el texto `el hijo verifico la carga` cuando el mensaje real es `hijo verifico la carga`. El
guardian estaba bien; la asercion del arnes estaba mal. Se corrigio la asercion y se re-midio
(7/7). No se "aflojo" ninguna asercion de la suite.

## 3. M48 - fix BUG-151 (GO punto 4)

### 3.1 Premisa medida, no heredada

- `AnimationService` es **autoload**: `project.godot` L85 `AnimationService="*res://scripts/animacion/animation_service.gd"`.
- El script cuelga del nodo `AnimacionM48` en `scenes/player/Player.tscn` (L45), asi que su
  `_ready()` SI corre en runtime.
- Sonda propia (Player.tscn instanciado, 2 frames, lectura de `_anim`) **antes** del fix:

```
ERROR: Failed to retrieve non-existent singleton 'AnimationService'.
SONDA M48: _anim=null _fsm=OK
SONDA M48: autoload_en_root=true
```

Es decir: el autoload EXISTE en el arbol y aun asi `Engine.get_singleton` devuelve null. El
`_process()` salia por el guard `if _fsm == null or _anim == null: return` (L54-55): **el
jugador no animaba nada en runtime**.

### 3.2 El fix y su efecto medido

`_anim = Engine.get_singleton("AnimationService")` -> `_anim = get_node_or_null("/root/AnimationService")`.

Sonda **despues**:

```
SONDA M48: _anim=NODO(AnimationService) _fsm=OK
SONDA M48: autoload_en_root=true
```

Sin `ERROR` de singleton. `--check-only` del archivo: EXIT 0 (sigue compilando en CI sin el
class cache, que era el motivo original del cambio de M118; la ruta de nodo no usa el
identificador del autoload).

Se actualizaron ademas los 2 comentarios que describian el mecanismo viejo (cabecera L13-14 y el
docstring de `_anim`), porque afirmaban que la referencia se habia reemplazado **por**
`Engine.get_singleton`: dejarlos habria sido una cita viva que describe el defecto como si fuera
la solucion. No se toco ninguna otra linea ni ningun archivo ajeno.
