## Cambios Realizados

### 1. FLIP #169 — claim «testeado» FALSO en el disparo por guardado

**Item:** `- [x] Implementar disparo del detector al guardar [S] — SaveManager.save_completed
(M59) → forzar_chequeo (testeado)` → **`[?]`**.

**El codigo de produccion SI esta correcto.** `softlock_guard.gd:75-76`:

```gdscript
if sm != null and sm.has_signal("save_completed"):
    sm.save_completed.connect(func(_slot: int, _reason: String): forzar_chequeo("guardado"))
```

Conexion con guarda `has_signal`, delega a `forzar_chequeo` que itera `_invariantes` y llama
a `_check_and_recover`. Lo mismo para transiciones (`:72-73`, `carga_iniciada`).

**El test es un falso-verde.** `test_anti_softlock_m66.gd:48-49`:

```gdscript
var handler := Node.new()
handler.set_script(load("res://scripts/core/invariants/irecoverable.gd"))
```

`irecoverable.gd` declara `class_name IRecoverable extends RefCounted` — el propio archivo
dice "se modela como RefCounted con duck-typing (no Node)". Aplicarlo a un `Node` produce en
**cada ejecucion**:

```
ERROR: Script inherits from native type 'RefCounted', so it can't be assigned to an object
of type 'Node'.  at: instance_create (modules/gdscript/gdscript.cpp:419)
    [0] _test_disparo_guardado (res://scripts/core/test_anti_softlock_m66.gd:49)
```

Consecuencia en cascada:
1. El script **no se aplica**; `handler` queda como `Node` desnudo.
2. `registrar_handler` solo hace `_handlers.append(handler)` (no invoca metodos de
   `IRecoverable`), asi que **no crashea** y la prueba sigue.
3. La unica asercion del bloque es `_check(true, "disparo por guardado sin crash")`
   (linea 54) — **literalmente siempre pasa**.
4. Exit code 0 → **gate CI verde a pesar del ERROR**.

El bloque documenta su intencion ("verificamos el efecto indirecto — que las invariantes
corran") pero **no mide nada**: ni las invariantes corrieron, ni el handler tenia la
interfaz, ni el efecto se observo.

### 2. Por que dos QAs previos no lo vieron

hy3 (Log 744) y Hy3 (Log 953) reportaron "0 fallos, exit 0". **Ambos leyeron el exit code,
no el stderr.** El ERROR esta ahi desde que glm-5.3-flash escribio el test (2026-09-01), y
el patrón `_check(true)` lo disfraza. **Leccion 20 confirmada por tercera vez en este
ciclo** (M11, M14, ahora M66): un QA que verifica exit codes esta haciendo QA de presencia,
no de comportamiento.

Mi verificacion estandar (re-ejecutar con binario real + inspeccionar **todos** los ERROR,
no solo SCRIPT ERROR de parseo) es lo que lo expuso. De ahora en mas, cualquier ERROR de
runtime en un test headless debe tratarse como sospechoso aunque el exit sea 0.
