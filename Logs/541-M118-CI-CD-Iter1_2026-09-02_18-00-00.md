## Pitfalls documentados (memoria colectiva)

- **`subprocess.run` y backslashes en Windows**: si el cmd es `[godot_bin, ...]`, los `\\` en el path se interpretan como escape chars. **Solucion**: `os.path.normpath(path)` antes de pasarlo a subprocess, o usar `subprocess.run([...], shell=False)` con paths ya normalizados.
- **`godot --path` debe apuntar al PROJECT, no al repo**: si el project esta en `game/isla-ancestral/project.godot`, el `--path` debe ser esa ruta, no la raiz del repo. **Solucion**: calcular `GODOT_PROJECT_PATH` separado de `PROJECT_ROOT`.
- **`fail_fast=False` para tests**: si quiero ver TODOS los tests que fallan, el pipeline no debe abortar en el primer fallo. **Solucion**: parametro `fail_fast` en Pipeline, default True para builds, False para tests.
- **Lint warnings vs errors**: tab al inicio no es un error fatal (muchos agentes lo hacen). Es un **warning** que no aborta el build. **Solucion**: warnings a stdout, exit code 0 si no hay errores; `errors` (errores de sintaxis) son los unicos que rompen el build.
- **Mismo `Step` con `cwd` opcional**: si step.cwd=None, usa el project_root. Si se setea, es independiente. Esto permite ejecutar steps en subdirectorios (ej: `build/`) sin perder el contexto global.

## Decisiones clave

1. **Pipeline en Python, no en PowerShell**: el plan original mencionaba `build_dev.ps1` (PowerShell) que es Windows-only. Mi pipeline Python corre en Windows, macOS y Linux. **Misma API, multiplataforma**.
2. **Data-driven via JSON**: el pipeline se puede definir en un .json (no en codigo). Esto permite que GitHub Actions, scripts locales, o un agente automatico invoquen el mismo pipeline.
3. **Reportes JSON machine-readable**: `out/ci-report.json` y `out/test-report.json` con timestamps, duration, ok/fail, errores. Esto se puede conectar a dashboards o notificaciones.
4. **Multi-path tests**: `run_tests.py` busca en `scripts/` Y `tests/`. El proyecto tiene 200+ tests en ambas carpetas. Sin esto, solo se ejecutaria la mitad.
5. **Sin sobreescribir codigo existente**: el M118 ya tenia BuildScript.cs y scripts PowerShell (citados en el plan). Yo NO los modifiqué; agregué una **capa Python** que coexiste. **Duck-typing del proyecto**: si los PowerShell existen, se usan; si no, se usan los Python.
